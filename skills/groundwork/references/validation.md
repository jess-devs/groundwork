# Validation

Run the relevant checklist before presenting an artifact. Fix what fails, then
present. If something cannot be fixed without information you do not have, mark
the line as an open question rather than filling the gap with a guess.

Run `scripts/check_docs.py` first, from wherever the skill is installed, with
`docs/` as its argument. `SKILL.md` shows the invocation. It settles the
structural lines
on this page without your judgement: broken identifier references, requirements
no story covers, stories with no criterion, decisions missing from the index,
pointers to files that are not there, a missing header block. Those items are
marked below with `[checker]`. What it reports is fixed before presenting, like
any other failure, and a line it cannot decide is still yours to read.

Report the outcome using the line defined in `SKILL.md`: the label, then three
counts in this order, each naming what it refers to, with the wording in the
working language (`SKILL.md` shows the English and Spanish forms). The report
goes in the message, never inside the artifact: a checklist result written into
the document is not a report, it is an unsupported claim sitting where the work
should be.

The first count is not chosen. It is the number of items below that apply to the
artifact being presented, counting the `Every artifact` block plus the block
named after the file. It is knowable before the check starts and can be counted
back against this page. The other two name what they refer to, always. A count
standing on its own is the part of the report that nobody can check.

## Before opening any phase

- [ ] The change is big enough that documenting it is worth less than the
      documentation. If not, say so, offer the short path, and stop here.

## Every artifact

- [ ] Written in the user's working language.
- [ ] Self-contained: understandable by someone who has this repository and
      nothing else. No references to "what we discussed".
- [ ] Inferred statements marked as inferred.
- [ ] No content invented to fill a section. An empty section with a note is
      better than a plausible fabrication.
- [ ] [checker] Header block present on every artifact without exception,
      including `decisiones.md`, with an honest status.
- [ ] [checker] Every internal reference points to something that exists: a
      file, a section, an identifier. Broken pointers are the most common
      self-sufficiency failure.
- [ ] No leftover text from an earlier edit: no explanation of a state nothing
      is in, no reference to a section since removed.
- [ ] No credential, token or connection string anywhere in the file.

## 00-contexto.md

- [ ] The problem is stated without naming a solution.
- [ ] Every user type listed has a stated need.
- [ ] The methodology has a name, a reason and a consequences line.
- [ ] The reason references specific factors of this project, not general
      properties of the framework.
- [ ] Glossary terms are used consistently in every other artifact.

## 01-alcance.md

- [ ] "Out of scope" is not empty. If nothing was excluded, nothing was decided.
- [ ] Each in-scope item is concrete enough to be recognisably done or not done.
- [ ] Assumptions are listed separately from confirmed facts.

## 02-requisitos.md and features/*/requisitos.md

- [ ] Every requirement has a unique identifier.
- [ ] Every non-functional requirement has a measurable threshold.
- [ ] Every non-functional requirement has a source traceable to something the
      user said. Delete or query any that were generated by habit.
- [ ] No requirement specifies an implementation. "Store passwords hashed with
      bcrypt" is a decision; the requirement is that stored credentials must not
      be recoverable.
- [ ] Feature requirements reference the system requirement they refine.
- [ ] No feature requirement adds scope its parent does not have. A refinement
      narrows; if it broadens, it belongs in `02-requisitos.md` first.

## features/*/historias.md

- [ ] Every story references at least one requirement.
- [ ] [checker] Every requirement in the feature is covered by at least one
      story. List any that are not.
- [ ] [checker] Every story has at least one acceptance criterion.
- [ ] Every criterion carries a `CA-<story-number>.<n>` identifier (e.g.
      `CA-01.1`), referenced by ID in `04-calidad.md`.
- [ ] Every criterion is checkable by observation, without interpretation. Apply
      the test: could two people disagree about whether it passed? If so,
      rewrite it.
- [ ] Non-functional requirements have stories too.
- [ ] No criterion describes how the code works internally. Criteria describe
      observable behaviour.

## Feature slicing (before writing any feature artifact)

- [ ] The slice serves one user role and one coherent flow.
- [ ] Roughly six stories or fewer.
- [ ] Named for what the user gets, not for the release.
- [ ] If everything landed in one slice, that was a decision. Justify it or
      split.

## features/*/plan.md

- [ ] The order is justified, not alphabetical or arbitrary.
- [ ] Dependencies between stories are stated.
- [ ] Assignment section present only if the team is a group.

## 03-arquitectura.md and decisiones.md

- [ ] Each decision lists alternatives that were genuinely considered. A single
      alternative named only to be dismissed is not a comparison.
- [ ] Each decision states its consequences, including costs. A decision with
      only benefits was not analysed.
- [ ] No decision contradicts an active decision elsewhere. If it does, the
      older one is marked superseded.
- [ ] Conventions stated here match what the existing code actually does, or the
      divergence is recorded as a decision.

## 04-calidad.md

- [ ] Every quality attribute traces to a non-functional requirement.
- [ ] The verification log has one row per criterion, not one row per story.
- [ ] Failures are recorded, not removed.

## Before implementation

- [ ] The story being implemented exists and is approved.
- [ ] Its acceptance criteria have been read in this session.
- [ ] Any new structural element has a decision recorded.

## After any phase or story that changed reality

- [ ] Scope discovered later is in `01-alcance.md`, and the open questions it
      answers are marked resolved.
- [ ] `plan.md` matches the order and dependencies actually followed.
- [ ] [checker] The decision index in `03-arquitectura.md` lists every decision
      recorded.
- [ ] `AGENTS.md` exists, carries the three execution rules in full, and every
      row of its table points at a file that exists. A repository with `docs/`
      and no `AGENTS.md` is a defect.
- [ ] An `AGENTS.md` that was already there was added to and not replaced:
      everything it said before is still in it, in the order it was in. If the
      repository uses `CLAUDE.md` for the same purpose, the rules went there
      instead of into a second entry point.
- [ ] No two artifacts contradict each other.
- [ ] Each piece of content is in the artifact that owns it: criteria and
      results in `04-calidad.md`, decisions in `decisiones.md`, order in
      `plan.md`. Environment troubleshooting belongs in none of them.

## After another skill produced the work

- [ ] Every acceptance criterion its work covers has been verified and logged.
- [ ] Decisions it took are in `decisiones.md`, including ones it took on its
      own initiative.
- [ ] Gaps it exposed that no criterion covers are named, not absorbed.
- [ ] Artifacts it wrote are referenced from `AGENTS.md`, with what they govern.

## Before closing a story

- [ ] Each criterion checked individually and recorded as pass, fail or blocked.
- [ ] Every `pass` cites something observed, not something inferred. If the
      evidence is a design guarantee, a library's behaviour, or a code review,
      the result is `blocked`.
- [ ] Any criterion nobody could ever observe is rewritten, not approved. A
      criterion that could be observed with a resource you do not have is not
      rewritten: it is `blocked`, and the resource is named.
- [ ] The blocked criteria are gathered into one request naming what would
      unblock them, not left as scattered rows for the user to reassemble.
- [ ] Test data, rows and accounts created for verification have been deleted,
      or the exact cleanup command was handed over for this story, checked for
      syntax before handing it over, not accumulated across stories.
- [ ] Only data created in this session was deleted, identified by what was
      recorded when it was created rather than by a pattern that matches it.
      Anything that could not be told apart from pre-existing data was left in
      place and named.
- [ ] Status updated in `historias.md` _and_ in `04-calidad.md`. Both, always.
- [ ] Any decision taken while implementing is in `decisiones.md`, including
      the small ones: a renamed file the framework forced, a changed shape of a
      shared type, a new config flag.
